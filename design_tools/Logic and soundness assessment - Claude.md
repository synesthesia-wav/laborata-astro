**Claude**

Checked the mechanism this time before assessing the content around it, and it's worth reporting because it changes the picture slightly: `/goal` in Codex CLI isn't a custom-prompt macro (the `/prompts:name` mechanism, which is just a saved Markdown template deprecated in favor of "skills"). It's a distinct, experimental feature — persistent goal mode, requires `goals = true` in config.toml, and it loops **plan → act → test → review → iterate autonomously until a stop condition is met**, not a single pass. OpenAI's own guidance for using it well is: give it an objective, a done condition, a scope, and constraints. That's a real, non-trivial thing to know, and the document you pasted maps onto that shape almost exactly — objective (the opening paragraph), done condition (the explicit "DONE WHEN" clause), scope ("INSPECT ONLY THIS COMPONENT... do not modify it yet"), constraints (the repeated "do not" lines). So this isn't loosely invoking a slash command for flavor — it's a competently-specified goal-mode spec, and that's worth crediting up front.

**The single load-bearing sentence is "record only problems you can actually reproduce. Do not predict failures from the code or report personal taste as a bug."** That's the mechanism that makes the rest of the design trustworthy, and it's worth naming why: it forces the evaluation function to be *reproducible* rather than the agent's own guess or aesthetic judgment. This is the exact property that was missing from the AutoResearch UI-recreation loop you had me review earlier — that one folded a VLM's subjective "does this feel production ready" judgment into the same automatic keep/discard gate, which reintroduces the ambiguity a sound ratchet needs to exclude. This document gets that right at component scale: confirm empirically, fix, re-render the *same* state, check it's actually gone, check nothing else regressed. That's a faithful, well-scoped instance of the discipline the earlier piece only gestured at.

**The scope discipline is also tighter than anything in the first document.** Two-phase structure (inspect-only, then fix-only-confirmed-problems), one fix at a time, explicit re-check against a fixed invariant list, and a hard boundary against scope creep ("do not use this as an excuse to redesign the component, change its public API, or touch functionality outside the test page"). No made-up thresholds, no "~1-3%" pseudo-precision — the done condition is binary and checkable (states rendered, confirmed problems fixed and retested, existing tests pass, build succeeds), not a fuzzy score.

Two real gaps, both implementation-level rather than conceptual:

1. **"Render every scenario side by side in one pass" risks contaminating the exact thing it asks you to verify.** Many instances of the same interactive component on one page can collide — duplicate ARIA ids, shared focus traps, shared global state — in ways a single mounted instance in real usage never would. The spec asks the agent to confirm "keyboard and focus behavior did not regress," but doesn't address instance isolation, so a false pass or false fail here is plausible and wouldn't be caught by anything else in the spec.
2. **It doesn't say how to force loading/error/permission-denied states in a component that fetches its own data internally.** "Use the real component... do not connect to production data" is fine when states come in through props, but a component with its own internal fetch hook needs some form of mocking or dependency injection to reach those states at all, and the spec is silent on how that's supposed to happen without violating "don't rebuild a lookalike" or "don't touch production data."

One smaller tension worth flagging: "select the stress cases that apply" requires reading the component's code, and "do not predict failures from the code" forbids reasoning from code to outcomes — the distinction (deciding what's *relevant* to test vs. predicting what *will happen*) is coherent on paper, but it's a fine enough line that an executing agent could blur it in practice, especially given the well-documented LLM tendency to hedge toward prediction rather than just running the thing.

Net: of the three pieces you've had me review today, this is the most mechanistically sound — the evaluation is grounded rather than judged, the scope is genuinely narrow, and the stop condition is concrete rather than invented. The weaknesses are about test fidelity (isolation, mocking self-fetching components), not about the logic of the loop itself.
